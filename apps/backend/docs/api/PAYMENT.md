# Payment API Reference

Covers payment intents, server-side Razorpay verification, signed gateway webhooks and scheduled reconciliation.

**Canonical source:** NestJS controllers and DTOs define the API contract. The OpenAPI document is generated from those decorators.

- **Interactive UI:** `GET /api/docs` where enabled
- **Machine-readable spec:** `docs/api/openapi.json` — regenerate with `npm run docs:openapi`

## Conventions

| | |
|---|---|
| Base path | `/api/v1` |
| Customer/provider endpoints | JWT bearer token; ownership is checked against the booking |
| Razorpay webhook | No JWT; requires the exact raw request body, `x-razorpay-signature` and `x-razorpay-event-id` |
| Internal reconciliation | No JWT; requires a timestamped HMAC generated by the dedicated Cloudflare Worker |
| Content type | `application/json` |
| Error shape | Standard API error envelope |
| Gateway selection | `PAYMENT_PROVIDER=razorpay` selects the real Razorpay adapter; stub is development/test only; disabled is the safe default in staging/production |
| Pilot safety | `PILOT_DISABLE_COLLECTIONS=true` blocks new cash/online collection and browser confirmation; signed webhooks still reconcile previously created gateway orders |

## Customer-facing (`/payments/me`)

### `POST /payments/me`

Example:

```json
{ "bookingId": "a1b2c3d4-...", "method": "ONLINE", "amount": 499, "clientRequestId": "uuid" }
```

Creates a payment intent against one of the customer's own bookings. The server serializes payment reservations per booking, uses a serializable transaction, and checks the outstanding balance against the immutable tax-inclusive price snapshot where available. Reusing `clientRequestId` with a different method or amount is a conflict.

- `ONLINE`: creates a Razorpay order when the real provider is enabled; returns its order id for checkout.
- `CASH`: creates an uncollected cash intent; no gateway call is made.

An initiated amount reserves part of the booking balance. A failed intent does not count as collected.

### `GET /payments/me`, `GET /payments/me/:id`

Lists or reads only the signed-in customer's payments. Optional list filters: `status` and `bookingId`.

### `POST /payments/me/:id/verify`

Example:

```json
{ "gatewayPaymentId": "pay_...", "gatewaySignature": "..." }
```

The backend verifies the checkout signature and then reads the payment from Razorpay. Only a captured payment with the expected order id, exact amount and currency is confirmed. Invalid signatures do not change payment state. Repeating verification for the same captured payment is idempotent; a different payment id cannot overwrite an existing capture.

## Provider-facing (`/payments/provider/me`)

### `GET /payments/provider/me`, `GET /payments/provider/me/:id`

Lists or reads payments associated with the signed-in provider's offerings.

### `POST /payments/provider/me/:id/mark-collected`

Records physical collection of a `CASH` intent only. It cannot confirm an online payment and cannot be repeated after success.

## Gateway webhook (Razorpay)

### `POST /payments/webhooks/razorpay`

- Headers: `x-razorpay-signature`, `x-razorpay-event-id`.
- Body: the original Razorpay JSON payload. The backend verifies HMAC-SHA256 over the untouched raw bytes using `RAZORPAY_WEBHOOK_SECRET` and a timing-safe comparison.
- Event identity is unique per provider. A duplicate processed event is acknowledged without applying the transition again.
- Only `payment.captured` / `order.paid` can confirm an online intent, and only when the order id, captured payment id, paise amount and currency match.
- `payment.failed` is recorded but does not immediately fail the order-level intent: Razorpay may allow another attempt against the same order.
- Only a minimal sanitized payload is persisted. Failed transient processing is queued with bounded exponential backoff; permanent mismatches enter `DEAD` for manual review.

The endpoint returns HTTP 202 for accepted/queued events. Invalid signatures are rejected; transient processing failures return a retryable server error so the gateway can redeliver.

## Scheduled reconciliation

### `POST /internal/payments/reconcile`

Private endpoint called by the Cloudflare Worker every five minutes. It accepts only a timestamped HMAC using `PAYMENT_RECONCILIATION_CRON_SECRET`, with a five-minute replay window. It:

1. retries due webhook inbox rows and expired processing leases;
2. checks older pending Razorpay orders against Razorpay's order-payments API;
3. confirms a single exact captured payment;
4. leaves uncaptured orders pending—absence of a capture is not proof of failure; and
5. surfaces multiple captures and reconciliation errors in the returned summary/worker logs.

Provision the Worker from `infra/cloudflare/payment-reconciliation-cron/wrangler.toml` and set `SEVAMITRA_API_ORIGIN` plus `PAYMENT_RECONCILIATION_CRON_SECRET`. The same secret must be configured on the API. Never expose it to browser/mobile clients.

## Remaining financial launch gates

- Refunds are not yet a real Razorpay refund integration; partial-refund ledgering, refund webhooks and idempotent recovery remain open.
- Payouts/settlements remain disabled until provider-account validation, idempotent payout execution and payout reconciliation are implemented.
- The `DEAD` webhook queue needs an operator review/replay UI and alert routing.
- Multiple captures need an audited manual-resolution workflow.
- Run sandbox E2E against actual Razorpay test credentials (duplicate/out-of-order callbacks, forged signatures, retries, timeouts, disconnects and reconciliation) before enabling public collection.
- Quote acceptance and cash/online collection UAT remain launch gates. A green CI run does not authorize live money movement.
